# 迭代一：修复真实模型返回格式与 AI 出题校验

## 1. 用户原始需求与问题

> “为什么报错了呢，生成的题目未通过校验，请调整要求后重试。你看一下.env.local 我已经填写了真实的apikey和baseurl。”

目标是：教师填写真实课堂内容后，由大模型生成单选、多选、判断、填空题，并通过统一的结构化校验。

## 2. AI 排查过程

AI 首先检查了配置文件和运行服务，但没有输出 API Key：

- `.env.local` 已存在；
- `AI_API_KEY` 已填写；
- `AI_BASE_URL` 和 `AI_MODEL` 均存在；
- `/api/config` 返回 `{"aiConfigured":true}`。

因此可以排除“服务没有读取到密钥”。

随后使用默认课堂内容“过拟合与模型泛化”调用真实生成接口，复现结果为：

```text
HTTP 422
错误信息：生成的题目未通过校验，请调整要求后重试
```

详细校验路径为：

```text
path: ["stem"]
message: Invalid input: expected string, received undefined
code: invalid_type
```

结论：模型接口和密钥可以工作，但模型返回的题目字段与系统要求的 Assessment Schema 不一致，题干字段 `stem` 缺失。

## 3. AI 修改建议与实施

AI 实施了四层修复：

### 3.1 明确 Prompt 的 JSON 字段模板

在 Prompt 中增加完整示例，要求每道题必须返回：

- `type`：题型；
- `stem`：题干；
- `options`：选项数组；
- `answer`：标准答案数组；
- `explanation`：解析；
- `knowledgePoint`：知识点。

同时禁止返回题目 ID、分值和 JSON 之外的说明，ID 与分值由服务端生成。

### 3.2 兼容常见模型字段别名

增加字段归一化处理：

- `question`、`questionText`、`title`、`题干` → `stem`；
- `choices`、`选项` → `options`；
- `correctAnswer`、`correct_answer`、`答案` → `answer`；
- `analysis`、`rationale`、`解析` → `explanation`；
- `knowledge_point`、`knowledge`、`知识点` → `knowledgePoint`。

题型同时兼容 `single`、`multiple`、`judge` 等常见写法以及中文题型名。

### 3.3 保留严格业务校验

没有因为兼容字段而放宽规则：

- 题量必须与教师要求一致；
- 题型顺序必须符合选择；
- 单选题只能有一个答案；
- 多选题至少两个答案；
- 答案必须引用已有选项；
- 判断题只能使用 `true` 或 `false`；
- 总分必须由服务端分配为 100 分。

### 3.4 改进错误定位

校验失败时返回具体题号和字段路径，不再只显示“生成失败”。

## 4. 验证与 Bug 修复结果

新增模型字段兼容、缺失题干定位、题型顺序三类测试，并使用用户配置的真实模型重新调用。

真实接口返回：

```text
HTTP 201
生成模式：ai
题目数量：6
题型顺序：single_choice、multiple_choice、true_false、fill_blank、single_choice、multiple_choice
总分：100
题干、答案和解析完整性：True
```

随后用户又提出“同一知识点的题目应相邻，组内按单选—多选—判断—填空排列”。AI 增加服务端确定性的 `organizeQuestions`，避免仅依赖模型自行排序。

对应提交：

```text
f4d5351 fix: 兼容真实模型题目字段并完善生成提示
682e64a feat: 按知识点分组并规范题目排列顺序
```

## 5. 该迭代体现的 AI 协同能力

- 先通过工具验证配置，不盲目修改密钥；
- 用真实错误定位 Schema 与模型输出的偏差；
- 同时改进 Prompt 约束和代码兼容性；
- 保留服务端业务校验，不让模型直接控制页面代码；
- 用真实 API 和自动化测试证明修复有效。

# 迭代二：从 JSON 文件迁移到 MySQL 持久化

## 1. 用户原始需求与问题

> “代码修改了吗，现在数据应该需要持久化到数据库里了。”

此前用户已要求创建智测云数据库和数据表。AI 执行了初始化 SQL，但应用仍使用 `data/database.json`。用户指出“建表成功”不等于“应用已经持久化到数据库”。

## 2. AI 对当前状态的确认

AI 明确承认：

> 之前只修改了数据库初始化 SQL 并创建了表，应用的数据访问代码还没有修改，页面仍然写入 JSON 文件。

随后确定改造原则：

- 保留现有页面和 API 行为；
- 使用 MySQL 8.x 作为真实业务存储；
- 使用 Drizzle ORM＋mysql2；
- 保留 `listQuizzes`、`createQuiz`、`createSubmission` 等原函数接口；
- 测验和题目、学生提交和逐题答案分别使用事务。

## 3. AI 修改建议与实施

### 3.1 数据访问层

新增：

- `src/lib/db/index.ts`：MySQL 连接池、UTC 时间配置、数据库健康检查；
- `src/lib/db/schema.ts`：与 MySQL 表对应的 Drizzle Schema；
- `DATABASE_URL` 环境变量配置；
- `/api/health` 数据库健康检查接口。

### 3.2 用事务替换原存储

- `createQuiz`：同一事务写入测验与全部题目；
- `updateQuiz`：同一事务更新测验、删除并重写草稿题目；
- `createSubmission`：同一事务写入整次成绩和逐题答案；
- 读取时将 MySQL 行映射回原有 Zod Schema，保持 API 数据契约不变。

### 3.3 防止重复提交

同时使用：

- 应用层学号重复检查；
- MySQL `(quiz_id, student_no)` 联合唯一索引。

即使两个请求并发提交，数据库约束也能兜底。

### 3.4 环境配置

在本机 `.env.local` 追加数据库连接地址，但不把密钥或真实配置上传到 GitHub。服务器使用独立配置文件。

## 4. 验证与 Bug 修复结果

执行真实 HTTP 冒烟流程：创建测验、发布、满分提交、零分提交、重复学号提交，然后直接查询 MySQL。

查询结果：

```text
测验状态：published
题目数量：6
题目总分：100
学生提交：2 份
逐题答案：12 条
满分学生：100 分
全错学生：0 分
重复学号：成功拦截
```

同时通过：

- 17 项单元测试；
- TypeScript 严格类型检查；
- Next.js 生产构建；
- `/api/health` 返回数据库已连接。

对应提交：

```text
0b7d7a4 feat: 初始化 MySQL 数据库与核心数据表
bdf11b3 feat: 将测验与作答数据持久化到 MySQL
```

## 5. 该迭代体现的 AI 协同能力

- 区分“数据库结构存在”和“应用真实使用数据库”；
- 保持原 API 契约，避免大范围重写；
- 通过事务保证业务数据一致性；
- 用数据库实际记录而不是页面截图证明持久化；
- 将唯一约束下沉到数据库，处理并发重复提交。

# 迭代三：教师登录、会话与权限隔离

## 1. 用户原始需求与问题

> “现在完成教师登陆的开发。”

目标是教师端必须登录后才能使用，学生继续免登录答题；每名教师只能管理自己的测验和学生成绩。

## 2. AI 修改建议与实施

### 2.1 首次教师初始化

提供 `/setup` 创建首个教师账号。初始化时直接升级原“本地系统账号”，使已有测验和学生作答自动归属于该教师，避免历史数据丢失。

后续又根据用户反馈：

- 密码最低长度从 10 位调整为 8 位；
- 登录方式从邮箱改为手机号；
- 登录页始终提供注册入口，支持多教师独立工作台。

### 2.2 密码安全

使用 Node.js 自带 `scrypt`：

- 密码以带盐的哈希保存；
- 不保存明文密码；
- 密码至少 8 位且包含字母和数字；
- 登录失败返回统一提示，并增加基础限流。

### 2.3 MySQL 会话

登录成功后：

- 生成随机会话令牌；
- 数据库只保存令牌 SHA-256 哈希；
- 浏览器使用 HttpOnly、SameSite=Lax Cookie；
- 公网 HTTPS 下启用 Secure；
- 退出时删除数据库会话并清除 Cookie。

### 2.4 页面和 API 权限

保护教师工作台、创建、编辑、发布、统计、学生详情和导出接口：

- 未登录页面重定向到登录页；
- 未登录 API 返回 401；
- 数据访问按 `teacherId` 过滤；
- 不知道或不拥有该测验时返回 404；
- 学生公开作答页面保持免登录。

## 3. 验证与 Bug 修复结果

AI 在独立的 `zhiceyun_test` 数据库中验证，避免测试账号占用正式首个教师账号。

验证通过：

- 未登录教师页面与 API 被拦截；
- 首次初始化、登录、退出和错误密码处理正常；
- 学生不带 Cookie 仍可作答；
- 第二名教师访问第一名教师的测验、详情和导出接口均返回 404；
- 学生公开页面返回 200；
- 23 项测试、类型检查和生产构建通过。

后续手机号迁移、题目内嵌分布和注册入口等真实 HTTP 验证也全部通过。

对应提交：

```text
d699a73 feat: 完成教师登录会话与数据权限隔离
2d271d8 fix: 将教师密码最低长度调整为八位
6e91786 feat: 改用手机号登录并内嵌题目作答分布
8749514 fix: 始终提供多教师注册入口
```

## 4. 该迭代体现的 AI 协同能力

- 不把“显示登录页”等同于真正权限控制；
- 同时在页面、API 和数据查询层验证身份与归属；
- 使用哈希而非明文保存密码和会话令牌；
- 用第二名教师验证越权访问，而不是只验证正常登录；
- 测试数据库与正式数据库隔离，保护真实数据。
