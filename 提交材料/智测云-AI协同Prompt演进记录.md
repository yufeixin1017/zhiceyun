# 一、真实模型返回格式与出题校验

## 问题定位

接入真实模型后，页面提示：

> “生成的题目未通过校验，请调整要求后重试。”

当时向 AI 提出的问题是：

> “为什么报错了呢，生成的题目未通过校验，请调整要求后重试。你看一下 .env.local，我已经填写了真实的 API Key 和 Base URL。”

检查配置文件和 `/api/config` 后，可以确认 API Key、Base URL 和模型名称均已被服务读取，因此问题不在密钥配置。

使用“过拟合与模型泛化”课堂内容重新调用接口，得到更具体的错误：

```text
HTTP 422
path: ["stem"]
message: Invalid input: expected string, received undefined
```

模型接口能够正常访问，但返回的字段与 Assessment Schema 不一致。系统要求题干字段为 `stem`，而模型可能使用 `question`、`title` 等字段，导致校验失败。

## 修改方案

### 明确输出结构

在 Prompt 中补充完整的 JSON 示例，要求每道题必须包含：

- `type`：题型；
- `stem`：题干；
- `options`：选项；
- `answer`：标准答案；
- `explanation`：答案解析；
- `knowledgePoint`：知识点。

题目 ID 和分值由服务端分配，避免模型生成不符合要求的标识或分值。

### 增加字段归一化

为兼容不同模型的返回习惯，增加以下映射：

- `question`、`questionText`、`title`、`题干` → `stem`；
- `choices`、`选项` → `options`；
- `correctAnswer`、`correct_answer`、`答案` → `answer`；
- `analysis`、`rationale`、`解析` → `explanation`；
- `knowledge_point`、`knowledge`、`知识点` → `knowledgePoint`。

题型同时兼容 `single`、`multiple`、`judge` 等常见写法和中文题型名。

### 保留严格校验

字段兼容不改变业务约束：

- 题量必须与教师选择一致；
- 题型顺序必须符合要求；
- 单选题只能有一个答案；
- 多选题至少有两个答案；
- 答案必须引用已有选项；
- 判断题只能使用 `true` 或 `false`；
- 服务端统一分配分值，总分为 100 分。

校验失败时会返回具体题号和字段路径，便于继续定位。

## 验证结果

修改后，使用真实模型再次生成同一份课堂内容，接口返回：

```text
HTTP 201
题目数量：6
总分：100
题型顺序：单选、多选、判断、填空、单选、多选
题干、答案和解析均完整
```

随后根据“同一知识点的题目应相邻，组内按单选—多选—判断—填空排列”的要求，增加服务端确定性排序，避免仅依赖模型自行组织顺序。

对应提交：

```text
f4d5351 fix: 兼容真实模型题目字段并完善生成提示
682e64a feat: 按知识点分组并规范题目排列顺序
```

这次迭代确定了“Prompt 明确结构、代码兼容差异、服务端保留业务校验”的生成方式，避免模型输出直接进入页面。

# 二、从 JSON 文件迁移到 MySQL 持久化

## 问题定位

数据库和数据表创建完成后，检查发现应用仍把业务数据写入 `data/database.json`。因此向 AI 提出了一个需要立即处理的问题：

> “代码修改了吗，现在数据应该需要持久化到数据库里了。”

这说明“数据库结构已经存在”并不等于“应用已经使用数据库”，需要替换真实的数据访问层，而不是只执行初始化 SQL。

## 修改方案

为保留现有页面和 API 行为，只替换底层存储：

1. 使用 Drizzle ORM 和 mysql2 建立 MySQL 连接池；
2. 按初始化表结构建立 Drizzle Schema；
3. 通过 `DATABASE_URL` 配置连接，敏感信息不进入 Git；
4. 保持 `listQuizzes`、`createQuiz`、`createSubmission` 等原函数接口；
5. 新增 `/api/health` 数据库健康检查。

两组写入分别使用事务：

- 创建测验时，测验和全部题目在同一事务中写入；
- 学生提交时，整次成绩和全部逐题答案在同一事务中写入。

重复学号同时由应用层检查和 MySQL `(quiz_id, student_no)` 联合唯一索引拦截，避免并发请求造成重复提交。

## 验证结果

通过真实 HTTP 流程创建并发布测验，再提交满分、全错和重复学号答案，随后直接查询 MySQL：

```text
测验状态：published
题目数量：6
题目总分：100
学生提交：2 份
逐题答案：12 条
满分学生：100 分
全错学生：0 分
重复学号：成功拦截
```

同时通过单元测试、TypeScript 类型检查和生产构建，`/api/health` 返回数据库已连接。

对应提交：

```text
0b7d7a4 feat: 初始化 MySQL 数据库与核心数据表
bdf11b3 feat: 将测验与作答数据持久化到 MySQL
```

这次验证以数据库中的实际记录为依据，而不是仅凭页面上的“保存成功”判断持久化是否完成。

# 三、教师登录、会话与权限隔离

## 问题定位

早期版本没有教师身份认证，知道教师端地址即可查看标准答案和学生成绩，也可以调用 AI 出题。因此提出：

> “现在完成教师登陆的开发。”

目标包括：教师必须登录，学生继续免登录；每名教师只能管理自己的测验和学生成绩。

## 修改方案

### 账号初始化

首次使用通过 `/setup` 创建教师账号。初始化时直接升级原“本地系统账号”，已有测验和学生作答自动归属于该账号，不需要额外迁移历史数据。

后续根据使用反馈，密码最低长度调整为 8 位，登录方式改为手机号，登录页始终保留注册入口，支持多教师独立工作台。

### 密码与会话

- 密码使用 Node.js 自带的 scrypt 哈希保存，不保存明文；
- 登录成功后生成随机会话令牌；
- 数据库只保存令牌的 SHA-256 哈希；
- 浏览器使用 HttpOnly、SameSite=Lax Cookie；
- 公网 HTTPS 下启用 Secure；
- 退出时删除数据库会话并清除 Cookie；
- 登录失败返回统一提示，并增加基础限流。

### 页面、接口和数据三层控制

1. 教师页面未登录时重定向到登录页；
2. 教师 API 未登录时返回 401；
3. 数据查询按 `teacherId` 过滤，非本人数据返回 404。

学生公开作答页面不强制登录，与教师管理接口分离。

## 验证结果

在独立的 `zhiceyun_test` 数据库中验证，避免测试账号影响正式数据：

- 未登录教师页面和 API 均被拦截；
- 初始化、登录、退出和错误密码处理正常；
- 学生不带 Cookie 仍可作答；
- 第二名教师访问第一名教师的测验、详情和导出接口均返回 404；
- 学生公开页面返回 200；
- 单元测试、类型检查和生产构建通过。

对应提交：

```text
d699a73 feat: 完成教师登录会话与数据权限隔离
2d271d8 fix: 将教师密码最低长度调整为八位
6e91786 feat: 改用手机号登录并内嵌题目作答分布
8749514 fix: 始终提供多教师注册入口
```

越权测试证明，权限控制不仅在导航和页面上生效，也在 API 和数据库查询中生效。
